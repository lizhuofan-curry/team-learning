# 团队知识库完整使用手册

适用于本团队的课程学习、实验记录、共享笔记和周报协作。本文按仓库实际提供的 Skill 与脚本编写；示例路径、日期、姓名和账号需要换成自己的，不表示队友已经完成接入。微信与语音仍应在每位成员的实际设备上验收。

## 1. 先分清这几个工具

| 工具或目录 | 负责什么 | 使用时要注意 |
|---|---|---|
| GitHub 团队仓库 | 保存三人同意共享的资料、版本与 PR 讨论 | 三人共用同一个远端，每人在电脑上克隆一份 |
| 团队仓库的本地克隆 | 编辑本次共享资料，提交后上传分支 | 本地保存后不会立即出现在 GitHub |
| 个人 Obsidian 知识库 | 保存本人原始材料、理解、试错及日记 | 每人独立；只选择适合共享的部分贡献到团队 |
| DeepTutor | 导入课程材料，检索、讲解、练习和辅助学习 | 团队 Git 更新后，DeepTutor 的索引不会自动更新 |
| Hermes + 微信入口 | 收集本人的学习原话、问题、计划和资源链接 | Hermes 实际运行在本地或服务器，收件位置随配置确定 |
| Codex 或能读文件的 Agent | 按 Skill 整理证据、知识与周报草稿，辅助准备 PR | 需要真实工具权限；AI摘要不能冒充本人理解 |
| 个人学习工作流目录 | 保存机器可读收件箱、草稿、审核记录和配置 | 与团队克隆分开，不上传整套私人运行目录 |

`Skill` 是 Agent 执行任务时读取的说明与工具包。它不是新的聊天模型，也不是安装后自动常驻的服务；仅在 GitHub 网页看到 `SKILL.md` 不代表自己的 Agent 已安装或读取它。

一次完整联动可以是：

```text
课件进入团队库 → 自己导入 DeepTutor → 针对困惑提问并核对
           ↓
微信告诉 Hermes：学了什么、还没会什么、下一步做什么
           ↓
本人专用收件箱 → Codex整理 → Obsidian来源、概念、日记及周报草稿
           ↓
本人确认周报精确版本 → 归档 → 选择共享记录 → 团队分支和PR
           ↓
队友审阅/复测 → 合并 → 所有人拉取 → 吸收进各自个人库
```

其中“导入”“真正使用”“独立掌握”“队友复测”分别记录。自动保存和自动整理不能替代学习与讨论。

## 2. 新成员第一次准备

### 2.0 只想把仓库链接发给Agent

首页分别提供[第一次资料贡献](../README.md)和[完整个人学习系统接入](../README.md#让-agent-带我完整接入个人学习系统)两段提示词，按本人目标选择。让 Agent 读取根 AGENTS 和[链接接入流程](Agent资料整理指南.md#从仓库链接开始)；完整接入走对应路线，不要求先提供团队贡献材料。普通网页聊天未必有电脑操作能力，不能操作时给本人当前可执行的一步并核对反馈，不假称已安装。不要只发网址就假定它已加载全部规则，也不用先安装三套全局 Skill。

### 2.1 需要哪些账号和软件

- 自己的 GitHub 账号，并接受本团队仓库邀请。
- Git；不熟悉命令行可使用 GitHub Desktop。
- Obsidian，用于打开自己的个人库，也可以另外打开团队克隆阅读。
- 能读取本地文件的 Agent；本团队示例使用 Codex。
- Python 3.9 及以上，用于仓库检查和学习工作流脚本。
- Hermes 与微信接入可稍后配置；暂时没有 Hermes 仍可手工输入学习记录。

团队远端是 [lizhuofan-curry/team-learning](https://github.com/lizhuofan-curry/team-learning)。本仓库现为公开，浏览不需协作者权限；推送团队分支仍需本人账号具备写入权限。推送失败时核对登录账号、邀请接受及权限，不要重新创建一个同名团队远端。

### 2.2 在自己电脑保留三个独立目录

Windows 示例：

```text
E:\团队知识库          ← GitHub团队仓库的本地克隆
E:\知识库\我的Wiki     ← 自己的Obsidian个人库
E:\学习工作流          ← 私人素材、草稿、审核及本机配置
```

盘符与目录由本人选择。macOS 使用自己的实际路径；不要复制别人 Mac 的 `/Users/姓名/...` 到 Windows。不要把团队克隆放进个人 Git 仓库，也不要把收件箱放进团队仓库。

### 2.3 克隆团队库

GitHub Desktop：`File → Clone Repository`，选择本团队仓库，指定空的本地目录后克隆。已有克隆时直接打开，避免克隆覆盖已有资料。

命令行方式：在目标目录的父目录执行：

```bash
git clone https://github.com/lizhuofan-curry/team-learning.git
```

该命令默认建立 `team-learning` 目录；可以在首次克隆时指定自己的目录名，例如 Windows：

```powershell
git clone https://github.com/lizhuofan-curry/team-learning.git "E:\团队知识库"
```

认证按 GitHub/GitHub Desktop 的登录流程完成，不把令牌写入命令、笔记或 PR。设置自己的 Git 姓名、邮箱，避免用其他成员身份提交。

### 2.4 没有个人库时，让 Agent 引导建立

在 Agent 中打开团队克隆，发送：

```text
请先读取 AGENTS.md，以及 .agents/skills/lab-knowledge-loop/SKILL.md
和 .agents/skills/lab-weekly-flow/SKILL.md，按新成员接入流程帮助我。
我还没有个人Obsidian库，请先让我选择个人库和私人工作流位置。
保留已有文件，团队使用当前共同远端，不新建另一个团队远端。
先完成最小个人库、团队克隆和文字记录；Hermes安装、微信扫码分步进行。
```

已有个人库时说明真实路径，要求沿用原目录和规则。最小新库可包含 `raw`、`wiki/sources`、`wiki/concepts`、`wiki/outputs`；旧库不必强行改成这种布局。

Obsidian 中选择“打开文件夹作为仓库”，打开个人库。再用同样方式打开团队克隆作为另一个仓库；两者是两个文件夹，不会因此自动互相复制。

接入工具的具体命令与边界见[首次接入](../.agents/skills/lab-weekly-flow/references/first-run.md)和[个人库与团队接入](../.agents/skills/lab-knowledge-loop/references/onboarding.md)。

个人库的首次私有 GitHub 同步、已有远端处理及 Obsidian Git 可选设置在[个人库指南](../.agents/skills/lab-knowledge-loop/references/onboarding.md#个人-git-与首次私有同步)集中维护。完整接入另外保存[私人进度与验证证据](../.agents/skills/lab-weekly-flow/references/onboarding-state.md)，恢复会话后从未完成项继续；不把空库初始化、同步文件或 CI 通过当作整套真实使用已验收。

## 3. 什么资料上传到哪里

| 内容 | 上传位置 | 应附带什么 |
|---|---|---|
| 专业课课件、讲义、练习及来源 | `课程资料/课程名/` | 课程README、作者/来源、版本和适用范围 |
| DeepTutor导入及使用记录 | `课程资料/课程名/使用记录/` | 实际导入材料、原问题、关键回答、引用核对、本人反馈和限制 |
| Agent Book实验 | `实验记录/项目名/第NN章/实验编号/本人账号/` | 目的、环境、命令、代码位置、输出、失败和分析 |
| 可复用的概念笔记、源码分析 | `共同知识/主题名/` | 作者、来源、核对状态、适用条件、未解决疑点 |
| 本人已确认的正式周报 | `周报/本人姓名/` | 实际周次、本人确认原文；附件按现有规则归档 |
| 操作说明、可复用模板 | `协作指南/` | 操作范围、真实入口和验证方法 |

资料可以是 Markdown、PDF、PPTX、图片或普通源码，关键是与课程/实验/知识主题相关、来源可说明、队友能使用。不为“凑齐目录”上传空模板，也不把保存过的全部文件一起上传。

不上传密钥、`.env`、私人完整聊天、Hermes账号缓存、个人 `config.local.json`、未审核草稿、个人机器可读收件箱、完整虚拟环境、模型权重和大型数据集。已经忽略的文件也要核对；不要用 `git add -f` 绕过保护。

附件放在所属课程或主题内部的“附件”目录，正文用仓库内相对链接引用。命名尽量让人看出课程、类型、章节/主题；不要用“未命名”“最终版副本”。Windows 不支持的字符与保留名称也要避免。

同一实验的每位成员使用自己的账号目录，主记录命名为`1-1_本人账号_实验记录.md`；不要三人都往同一位置上传`实验记录.md`。代码和附件保留在本人目录中，详见[文件组织规范](文件组织规范.md)及[实验记录模板](模板/实验记录模板.md)。

### README、资源索引、manifest有什么区别

- 实际 PDF/PPTX/代码：真正要学习的材料。
- 课程或主题的 `README.md`：这一小类资料的使用入口，列清谁负责、有哪些文件、完成到哪里。
- 根目录[资源索引](../资源索引.md)：团队的总目录，主要连接各课程和项目入口，避免把所有细节堆到首页。
- `manifest.json`：机器可读的资料登记册，通常用固定字段存路径、来源、大小与哈希。本团队目前不要求额外手写一套 manifest；继续维护已有 Markdown 索引即可。

例如新增计算机网络第二章课件：放进课程“课件”目录，在计算机网络 README 加入口和来源；若原有课程总入口不变，不必再建一个并行总索引。分工只维护[成员与课程覆盖](../分工与课程覆盖.md)，不要到处维护不同版本的负责人表。

## 4. 三套Skill分别怎么用

下列调用提示词适用于成员自己的课程、阅读、实验和项目；主题、路径与目标目录均取本次真实输入。计算机网络及发送时延只在历史实例中示范，不构成默认任务。

在 Agent 中打开本地团队仓库根目录，先读取[AGENTS.md](../AGENTS.md)。支持项目 Skill 的 Agent 可以按描述匹配；未显示时直接提供下面的文件路径，不必等待自动发现。

### 4.1 学习后整理知识：lab-knowledge-loop

入口：[知识联动Skill](../.agents/skills/lab-knowledge-loop/SKILL.md)。

```text
请读取 .agents/skills/lab-knowledge-loop/SKILL.md。
本次学习主题或项目：填写实际主题。材料与证据文件：填写实际路径。
请按资料类型整理课程学习、阅读、实验或项目记录，按需使用DeepTutor。
我的个人库位置是：填写实际路径。我的困惑和反馈是：填写本人原话。
保留原材料、真实结果、本人反馈与纠错过程；有问答时保留原问题和原回答。
区分AI解释和我的理解，先查已有知识再更新；不套用教程中的示例课程或问题。
给出适合共享的内容清单；只整理我明确选择的团队资料，不全量复制个人库。
```

产物通常是来源记录、概念增量、关联链接、学习日记及候选共享记录。尚未完成的练习、实验、复现或应用验证仍标记待做；验收方式按实际任务选择，不能因AI能解释就写“已熟练掌握”。

### 4.2 微信记录、日记和周报：lab-weekly-flow

入口：[周报工作流Skill](../.agents/skills/lab-weekly-flow/SKILL.md)。

```text
请读取 .agents/skills/lab-weekly-flow/SKILL.md。
我的私人工作流根目录是：填写实际路径。
同步指定日期的Hermes学习素材和可访问的Codex学习对话，区分成果、计划与问题。
核对上一期下周计划，更新个人日记和本周待审核稿，保留我已修改的内容。
标明读取范围、截至日期、缺失项和版本；未获我确认不正式归档或发送邮件。
```

没有 Codex 会话读取工具的 Agent 可以使用本人提供的摘录，必须说明未自动读取的范围。Skill 不会因为安装而获得所有应用聊天记录。

### 4.3 整理共享资料、准备PR：team-learning-materials

入口：[资料整理Skill](../.agents/skills/team-learning-materials/SKILL.md)。

```text
请按 .agents/skills/team-learning-materials/SKILL.md 整理指定资料。
输入：填写实际文件路径。
资料类型：课程资料/实验记录/共同知识/已确认周报；按本次实际材料选择。
所属课程、项目或主题及目标目录：填写实际值；未确定时先查已有目录再建议。
查重，保留来源、真实结果和待核对项，更新所属README与必要索引。
运行仓库检查，列出改动；经我授权后推送独立分支并创建本任务的PR。
不要改动其他成员资料，也不要把个人收件箱或配置加入提交。
```

个人知识整理、周报生成、团队提交是三个任务，不需要每次把三套 Skill 全执行一遍。更多完整提示词见[Skill使用指南](Skill使用指南.md)。

## 5. Hermes怎么接微信并保存学习素材

### 5.1 安装与微信接入顺序

已有 Hermes 和微信连接的成员跳过安装。未接入者按[部署与微信接入](../.agents/skills/lab-weekly-flow/references/deployment.md)执行，先确认实际运行方式是原生应用、CLI、WSL还是云端；不同版本先查 `hermes --help` 与 `hermes gateway --help`。

1. 从 Hermes 官方安装说明选择自己系统对应方式。
2. 配置自己的模型，先验证普通对话。账号和 Key 在本机设置中配置，不贴进聊天或团队仓库。
3. 在真正运行 Hermes 的机器执行 `hermes gateway setup`，按当前向导选择 Weixin/WeChat，由本人手机扫码及确认。
4. 按向导限定自己的私聊身份；不要默认开放给所有人。
5. CLI方式运行 `hermes gateway run`；桌面端已管理网关时不再重复启动。发一条普通微信消息，确认有回复，再接学习采集。

扫码成功只证明授权完成，普通消息往返与学习采集还要分别测试；私聊连接也不表示能读取全部微信群和历史消息。

### 5.2 本地Hermes的专用收件箱在哪

由安装时选择的 `--workflow-root` 决定。例如本人选了 `E:\学习工作流`，文件通常为：

```text
E:\学习工作流\收件箱\日期\素材编号.json
```

它不是微信界面里的文件夹，也不是自动出现在 Obsidian 左侧的笔记目录。Hermes实际数据目录由自己的安装或profile决定；不要照抄另一人的 `~/.hermes` 或 Windows路径。

Windows PowerShell 示例，在团队克隆根目录执行；替换路径后再运行：

```powershell
$skillDir = (Resolve-Path ".agents/skills/lab-weekly-flow").Path
$flowRoot = "E:\学习工作流"
$hermesHome = "替换为自己的Hermes真实数据目录"
py -3 "$skillDir/scripts/install_hermes.py" --hermes-home "$hermesHome" --workflow-root "$flowRoot"
py -3 "$skillDir/scripts/configure.py" --root "$flowRoot" --mode local --personal-vault "E:\知识库\我的Wiki" --weekly-archive "E:\周报" --obsidian-reports "E:\知识库\我的Wiki\wiki\outputs\周报"
```

已有归档位置时保留原位置；旧库不是 `raw/wiki` 布局时换成本人实际选择的目录。希望另存微信原话到专用 raw 目录时，让 Agent说明新增位置后再配置 `--archive-wechat-originals`，其他 raw 资料保持不改。macOS 将 `py -3` 换成 `python3` 并使用本机路径。

安装器只安装学习采集功能，不安装 Hermes本体、不替代模型设置、不修改微信账号。安装后让 Hermes 读取新 `lab-learning-capture` 技能，必要时新开对话。

### 5.3 云端Hermes与本地有什么不同

云端模式先写入 Linux 服务器的专用收件箱，再通过本人 SSH 配置同步至电脑。本人电脑上的 Codex 负责知识整理，服务器只需要采集技能和桥接脚本，不必安装 Codex。

```powershell
py -3 "$skillDir/scripts/configure.py" --root "$flowRoot" --mode cloud --remote-host "自己的SSH别名" --remote-root "/服务器绝对路径/.hermes/lab-learning"
py -3 "$skillDir/scripts/learning_flow.py" --root "$flowRoot" sync
```

前提是服务器端已经按部署说明安装采集脚本，且 `ssh 自己的SSH别名` 能正常连接。不要把上面的 Linux 路径换成 Windows盘符，也不要将其他人的服务器配置复制过来。

### 5.4 一条真实文字记录怎么发送

以下为填写模板；先替换为本人实际记录再发送，不将占位文字或教程示例当作经历：

```text
使用 lab-learning-capture 技能，记录学习：
实际发生日期：填写日期。今天实际完成：填写本人经历与证据。
仍未完成或遇到的问题：填写实际情况。下一步计划：填写本人计划。
请保留我的原话和日期，存入学习收件箱并返回编号。
```

检查它是否返回素材编号、日期与保存位置。再让 Codex 核对同编号文件；云端模式先 `sync`。同一素材重复同步不应生成重复成果。

如果想在 Obsidian 中看到原话，还需配置原话专用归档目录并运行 `archive-captures`。机器收件箱里的 JSON、Obsidian 原话 Markdown、AI摘要和概念笔记是不同层次，不能混为一份。

配置已经明确选择原话归档位置后，可运行：

```powershell
py -3 "$skillDir/scripts/learning_flow.py" --root "$flowRoot" archive-captures
```

它只新增真实微信本人原话，不会把测试或AI摘要写进raw；生成概念和学习日记仍需Agent另行整理。

### 5.5 可选自动采集与双向协作

默认首次安装不替成员启用后台采集或调度。希望正常学习提问也自动记录时，按[自动采集说明](../.agents/skills/lab-weekly-flow/references/automatic-capture.md)配置并验收当前回合观察器；明确不记录、无关话题、待核对语音及原话分开处理。

希望Hermes看到Codex进展、Codex收到微信修改意见时，按[双向协作说明](../.agents/skills/lab-weekly-flow/references/collaboration.md)设置自己的工作流目录和可选传输任务。文件送达、Agent已读、草稿已改好分别核对；传输任务不自动运行模型或批准周报。Mac每分钟传输和每日23:00整理属于分别配置的任务，不能推定队友也已启用。

### 5.6 语音、文章与视频怎样处理

- 语音先看真实转写，特别检查数字、单位、姓名和技术词。保留原转写及纠错，不能用AI润色稿冒充逐字原话。当前语音链路仍需本人方便时实际复测。
- 文章链接可先采集；只有实际读到正文，才能写已阅读。登录受限、抓取失败时请提供正文/PDF，不能只靠标题概括。
- 视频优先使用真实字幕、讲义或本人提供的转写；只有字幕时注明未核对画面。收藏链接不等于已学习，平台链接也不保证都能自动解析。
- 本工作流传输脚本不调用模型，也不负责语音识别；Hermes已有模型/STT能力与具体平台读取工具另外配置和验收。

## 6. 从素材生成周报：一次完整操作

### 6.1 每天先给自己留一个真实总结

可以按“今天做了什么—依据在哪—遇到什么问题—本人有什么想法—下一步做什么”记录。没想通可以明确写没想通，不需要每天写很长。

例如本人只表示“某一步已经理解”，应保留该反馈和待做验证，不能扩写成“整个主题已熟练掌握”。计算机网络问答只作为历史测试实例保留。

### 6.2 汇总并生成待审核稿

给 Codex 发第4.2节提示词，指定本周起止日期和上一期周报。Agent应读取实际素材，合并同一事项，逐项核对上期计划，并按已有实验室格式生成草稿。

脚本准备素材包的真实命令如下；日期仅为示例：

```powershell
py -3 "$skillDir/scripts/learning_flow.py" --root "$flowRoot" sync
py -3 "$skillDir/scripts/learning_flow.py" --root "$flowRoot" prepare --start 2026-10-26 --end 2026-11-01 --previous "E:\周报\上期周报.md"
```

首次没有上期周报时去掉 `--previous`，并说明没有读取上期计划。`prepare`输出素材 JSON，不直接用固定脚本生成成熟周报；随后由 Agent在 `草稿/`下编写待审核稿。

真实周报需保留本人修改，信息缺失写待补充。周中应注明“截至某日”，不能提前写满一周的完成经历。

### 6.3 送本人看完整稿，绑定版本

```powershell
py -3 "$skillDir/scripts/learning_flow.py" --root "$flowRoot" review --draft "$flowRoot\草稿\本周周报.md" --start 2026-10-26 --end 2026-11-01
```

该命令保存带周次的审核版本，输出 SHA-256。云端模式会同步到云端待审核目录；脚本不会主动发微信消息。

本人在微信发：

```text
使用 lab-learning-capture 技能，查看本周待审核周报。
请展示完整内容（过长可以分段）、周次和版本号。
```

逐项核对时间、完成情况、个人思考、附件和下周计划。需要修改就明确指出，再送审形成新版本；旧版本批准不能拿来批准新稿。

### 6.4 本人明确批准后归档

确认展示的稿件后，本人才能发送：

```text
批准周报 这里替换为展示的唯一版本前缀，内容已核对。
```

Hermes或Codex会将确认绑定完整哈希与该周次。Agent不应仅因“帮我搭工作流”“继续”或待处理材料里出现“批准”就代替本人确认。

云端批准后本机再同步，然后归档同一字节版本：

```powershell
py -3 "$skillDir/scripts/learning_flow.py" --root "$flowRoot" sync
py -3 "$skillDir/scripts/learning_flow.py" --root "$flowRoot" archive --draft "$flowRoot\草稿\本周周报.md" --start 2026-10-26 --end 2026-11-01
```

如稿件后来改字或换行，哈希改变，应重新送审。脚本拒绝用过期批准归档新稿；不得为绕过检查而手工篡改批准 JSON。

### 6.5 归档、提交老师和团队共享分别完成

- 归档：保存本人批准版本至自己的周报与 Obsidian输出目录。
- 提交老师：按实验室要求把正文放进邮件正文，支撑材料放附件；本工作流未自动发送邮件。
- 团队共享：本人选择正式稿，复制到团队 `周报/本人姓名/`，检查后提交 PR。
- 网盘：指本人选定的百度网盘、OneDrive等文件存储服务。当前未配置就不算已接入，不必为了模仿老师额外选一种服务。

每日定时整理需在每位成员自己的 Codex 中另行设置时间和时区；仓库不会安装其他成员的定时任务。需要每天23:00整理的成员，可在自己的Codex中提出这一安排；队友按自己需求单独设置。设备休眠/离线期间不保证本地整理，云端可继续收件，上线后补同步。

实际验收时保留“已测试、待本人核对、未配置”清单。没有本人展示及批准精确周报版本的证据，就不能称真实周报审核链路已经完成；没有实际正文、字幕或音频就不能称媒体内容已经读取。

## 7. 上传到GitHub：保存、Commit、Push和PR

| 动作 | 发生了什么 | 队友能否在main看到 |
|---|---|---|
| 在Obsidian或编辑器保存 | 文件写到本机 | 不能 |
| Commit | 给本机改动建立一份带说明的版本 | 不能 |
| Push | 将提交上传到远端对应分支 | 该分支能看到，main还没有 |
| 创建PR | 请求把自己的分支合入main，展示差异供审阅 | 尚未合并 |
| Merge | 接受本次PR进入main | 远端main可以看到 |
| Pull | 将远端更新取回本机 | 本机也更新了 |

个人库可以使用本人选定的 Obsidian Git 自动提交/推送，用于个人备份。团队库使用独立分支和PR，避免把未整理内容自动推入main；不要直接照搬个人库的全自动上传设置到团队main。

个人库需要手工填写提交说明时，Obsidian Git插件的 `Commit-and-sync with specific message` 表示“输入本次说明并提交、同步”，其暂存范围由当前设置决定，可能包含全部改动；仅 `Commit` 建立本机提交，是否上传需看后续 Push。首次按[插件操作步骤](../.agents/skills/lab-knowledge-loop/references/onboarding.md#obsidian-打开与可选-git-插件)核对暂存范围。自动提交、推送和拉取分别设置，应先完成一次手动同步并核对远端，再启用本人选择的周期；字段含义以已安装版本为准。自动上传不等于自动审阅。

### 7.1 GitHub Desktop流程

1. 打开团队仓库，确认没有混入上次任务或别人的未提交修改。
2. `Current Branch`切换 `main`，`Fetch origin`；有更新时 `Pull origin`。
3. `Current Branch → New Branch`，起名例如 `yourname/network-unit-notes`。
4. 编辑本次文件。新增内容先按第3节归位，不散放到根目录。
5. 在 `Changes`查看每个文件及差异，只勾本次需要提交的文件。
6. Summary写清改动，例如“补充计算机网络单位换算记录与待验证题”；再执行当前分支的Commit。
7. 首次上传分支使用 `Publish branch`，后续提交使用 `Push origin`。
8. `Create Pull Request`打开GitHub，确认目标为本仓库 `main`，填写PR模板。

按钮文案可能随 Desktop 语言/版本变化，以分支与差异状态为准。Commit成功不等于Push成功，创建PR也不等于已合并。

### 7.2 命令行流程

在团队仓库根目录执行；分支名和路径换成实际值：

```bash
git status
git switch main
git pull --ff-only
git switch -c yourname/network-unit-notes
# 在编辑器完成本次改动
python3 scripts/check_layout.py .
python3 scripts/check_docs.py .
git add 课程资料/计算机网络/使用记录/本次记录.md
git diff --cached
git commit -m "补充计算机网络单位换算使用记录"
git push -u origin yourname/network-unit-notes
```

Windows把 `python3`换成已安装可用的 `python`或`py -3`。`git add`使用实际文件路径，不照抄不存在的示例；有多个相关文件时逐一添加。先检查 `git status`，有未提交修改或冲突时先处理，不强行切换或覆盖。

之后在GitHub创建PR：通常从分支页面的 `Compare & pull request` 或 `Pull requests → New pull request`进入，核对 `base: main`、`compare: 自己的分支`。

### 7.3 PR说明写什么

使用自动出现的[PR模板](../.github/pull_request_template.md)，写清：

- 这次新增/修改了什么，以及放在哪里。
- 来源、版本与本人实际完成到哪一步。
- 哪些内容经过AI辅助，哪些是本人原话。
- 本地检查命令、结果与没有验证的部分。
- 请队友重点核对一个具体问题，例如“发送时延换算和课件页码是否对应”。

没检查的框不要勾选，不能预填“队友已确认”。未完成可先开Draft PR，准备好后再请求审阅；同一任务继续修改原分支即可，PR会自动更新，不必反复新建PR。

## 8. 怎样审查队友的PR

### 8.1 看什么、按什么顺序看

1. 在GitHub进入 `Pull requests`，打开队友PR，先读目的、来源、验证与待核对项。
2. 确认PR目标为main、改动范围合理；一份课程笔记不应附带密钥或整套私人工作流。
3. 打开 `Files changed`看真实差异，不只看作者描述。
4. 课程资料核对来源与版本，打开附件；DeepTutor记录抽查问题、回答与课件页码是否对应。
5. 实验记录核对命令、环境、输出和结论；教材结果、离线复核与本人真实运行应分开。
6. 共同知识抽查定义、推理或公式，确认引用能支持结论。
7. 周报只核对共享范围、格式与本人确认状态，不替别人补造经历或改写成自己的观点。
8. 看 `Checks`，确认对应的是最新提交，不把旧版本绿勾当作新版本通过。

最少认真检查一处关键结论并留下具体依据。“看起来不错”“AI说没问题”不能替代实质审阅。

### 8.2 怎么留下审阅意见

在 `Files changed`将鼠标移到具体行，使用行旁的“+”添加评论；可以开始一组审阅后统一提交。在 `Review changes`中选择：

| 选项 | 适合情况 |
|---|---|
| Comment | 提问、补充建议，暂未作通过判断 |
| Request changes | 发现会影响正确性或使用的问题，需要修改 |
| Approve | 已核对本人负责的范围，可以合并 |

账号权限、仓库设置和界面版本会影响可用操作；作者不能把自己的审核当作另一成员的批准。PR发起人应在同一分支修正并回复处理情况，审阅者确认问题解决后再处理讨论状态。

可参考这样的具体评论：

> 我对照课件复核了1B转8bit及速率的十进制换算，结果一致。记录中的“已掌握”缺少独立变式题，请改为“提问后解决困惑，变式题待做”。

这只是表达示例，不代表已有队友实际作出该核对。

### 8.3 合并前与合并后

合并前核对：最新CI通过、提出的问题已处理、需要的成员审阅实际发生、没有冲突和意外文件。由有权限的成员按团队约定点击 `Merge pull request` 并确认；若平台启用了必须审阅或其他保护，需要满足条件，不能禁用保护绕过。

团队可选择统一的合并方式。新手按当前仓库提供的方式操作；不熟悉时不要为清理历史执行force push。删除已合并分支是可选清理动作，先确认确已合并且不再使用。

合并后其他成员在干净工作区切回main并拉取：

```bash
git switch main
git pull --ff-only
```

GitHub Desktop同样切回main并Fetch/Pull。开始下一项任务再从最新main新建分支。吸收团队知识时记录具体文件与提交版本，并补本人理解，不把团队成果整库复制为个人原创。

### 8.4 需要在自己电脑复测队友的PR时

只看文档的PR可以在网页逐项核对；涉及链接、附件或脚本行为时，可以取到本地检查。先保存并提交自己的任务改动，确认 `git status` 没有未提交文件或冲突，再切换。不要把审查过程中的试改混入自己的其他任务。

以下**假设**要审查PR #12；数字只是示例，需换成GitHub上实际PR编号。本地审查分支名也应选未使用的名称：

```bash
git status
git fetch origin pull/12/head
git switch -c review/pr-12-check FETCH_HEAD
# 先读差异和说明，再打开资料并运行与改动相关的检查
python3 scripts/check_layout.py .
python3 scripts/check_docs.py .
git status
```

Windows将 `python3` 换成可用的 `python` 或 `py -3`。复测脚本前先读相关改动和运行条件，不运行来源不明的命令或把自己的账号配置复制到PR目录。课程PR应实际打开材料、抽查引用；脚本PR只运行与本次改动相关的测试，不需要每次重新部署Hermes。

复测完成，工作区保持干净后回到main：

```bash
git switch main
git pull --ff-only
```

然后到GitHub的该PR留下**实际核对的范围、结果和问题**，再选择Comment、Request changes或Approve。本地检查通过不会自动替你提交审阅意见。不要直接向队友的任务分支Push改动；需要修改时先在PR中说明，由作者在原分支处理，或明确协商后操作。

作者后来又推送了新提交时，应重新拉取该PR并核对新的差异；不要把旧检查结果写成最新版本已经通过。再次取PR时可使用新的本地审查分支名，保留原审查快照，不强行覆盖已有分支。

### 8.5 自己的PR与main发生冲突时

冲突表示双方改动无法自动拼接，并不表示必须删除其中一方。由PR作者在**自己的任务分支**处理；不要在main上编辑冲突，也不要为了绿勾覆盖队友内容。

先确认工作区没有未提交修改，再执行；分支名换成自己PR的真实分支：

```bash
git status
git fetch origin
git switch yourname/network-unit-notes
git merge origin/main
```

若自动合并完成，重新检查并Push即可。若提示冲突，运行 `git status` 找到冲突文件。在编辑器中查看 `<<<<<<< HEAD`、`=======`、`>>>>>>> origin/main` 两侧改动：HEAD是自己的任务分支，另一侧是刚取回的main。结合PR目的保留双方正确内容，删去冲突标记；涉及他人的原话、实验数据或结论时先与作者核对，不机械选择“全部保留当前”或“全部保留传入”。

解决后逐一加入实际文件、复查并完成合并提交：

```bash
git add 课程资料/计算机网络/使用记录/实际冲突文件.md
git diff --cached
python3 scripts/check_layout.py .
python3 scripts/check_docs.py .
git commit
git push
```

`git add`路径是示例，要换成所有实际解决的冲突文件。提交后原PR会自动更新，等待最新CI并请审阅者复核变化。

如果正在合并且无法判断如何处理，可以先停止本次合并：

```bash
git merge --abort
```

这会尝试回到发起合并前的状态，所以前面要求干净工作区。若Git提示无法中止，保留当前文件和报错，请队友或Agent逐项确认；不要直接 `reset --hard`、删除 `.git` 或force push。双方只是同时新增不同文件时通常可自动合并，也不必为避免所有冲突而让一人代替三人提交。

## 9. Actions、AI审查和同伴互审有什么区别

| 层次 | 本仓库的作用 | 不能证明什么 |
|---|---|---|
| 文档与附件Actions | 检查目录、命名、链接、附件及检查器回归 | 不证明课件正文、公式和实验结论正确 |
| Skill跨平台CI | 检查脚本在Windows/Linux、对应Python版本的行为 | 不证明每位队友的微信、语音与模型账号已通 |
| Codex AI代码审查 | 分析PR代码改动并提出疑点 | 没评论不代表全文正确，也不等于队友已审阅 |
| 队友实际审阅 | 理解内容、核对关键事实并反馈 | 只能说明实际检查过的范围，不保证无限覆盖 |

是否启用自动代码审查，既要看设置，也要看新提交是否产生实际审查记录。连接失败、额度限制或旧提交的审查不能当作最新版本通过。代码审查设置与GitHub Actions脚本是不同组件。

本地例行检查：

```bash
python3 scripts/check_layout.py .
python3 scripts/check_docs.py .
```

只有修改检查器或需要排查其行为时，再运行相关 `tests`。Skill维护者可按[Windows验收](../.agents/skills/lab-weekly-flow/references/windows.md)执行工作流核心与CLI测试；普通上传课件不要求反复运行全部工程测试。

## 10. 日常节奏和联动验收

建议三人先完成一次小循环，再扩展课程覆盖：

| 时点 | 本人动作 | 团队动作 |
|---|---|---|
| 每次学习后 | 保存原问题、证据和本人反馈；微信记录真实进展 | 有值得共享的结论时提交资料 |
| 每天结束前 | 补充问题和计划；查看日记是否准确 | 不要求每天凑一个PR |
| 每周 | 核对上一期计划、审阅周报、按要求提交老师 | 简短交流、轮换审阅、复测一项共享资料 |
| 资料变更后 | 更新个人理解；必要时重新导入DeepTutor | 原分支补提交，处理CI与队友反馈 |

真正有效的联动，应能拿出：一条真实素材、对应日记/来源、一份本人审核的周报、一个队友有具体意见的PR、一次拉取后的实际使用记录。目录齐全、自动脚本存在和AI写了很多内容都不能单独代替这些证据。

截至2026-10-28，主线已有29份主实验记录及支持材料、4期本人确认周报、计算机网络流程测试入口与真实使用反馈、共享概念，以及三套Skill。自动学习采集与双向协作的通用实现已合并；成员部署与真人验收分别进行。队友的实际个人库、微信/语音、课程认领、独立练习与互审情况需由各成员补充，不能由本手册认定完成。历史分工表如果与当前邀请或学习状态不一致，应按本人真实情况更新。

## 11. 常见问题

| 问题 | 先检查什么 |
|---|---|
| GitHub看不到刚写的文件 | 是否只保存未Commit、只Commit未Push，或正在看main而文件在任务分支 |
| 文件很多，怕提交隐私 | 查看Changes或`git diff --cached`；只选本次文件，不使用强制添加 |
| PR检查失败 | 打开对应失败步骤，看文件、行号与原因；修复后推送同一分支 |
| pull提示冲突或不能快进 | 保留本机修改和错误信息，让Agent解释；不删除.git、不reset覆盖 |
| Agent找不到Skill | 在本地打开仓库根目录，让它显式读取AGENTS.md和目标SKILL.md |
| 微信记录有编号，Obsidian没看到 | 先找真实工作流收件箱；云端先sync，再核对原话归档配置与日记整理是否执行 |
| 周报拒绝归档 | 核对周次、哈希、当前稿与本人真实批准；改稿后重新送审 |
| 自动任务没运行 | 核对本人的自动化、时区、电脑在线和实际覆盖记录；上线补查遗漏日期 |
| DeepTutor搜不到新上传资料 | Git上传不等于入库；检查正确课程库、导入状态及索引更新 |
| 语音技术词错了 | 先用文字记录，保留原转写疑点；单独复测，不默认切换外部语音服务 |

完整规则以[协作约定](协作约定.md)、[文件组织规范](文件组织规范.md)及实际Skill为准；说明与软件版本不符时先核对当前帮助和日志，再修订手册。
