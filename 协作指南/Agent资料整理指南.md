# Agent 资料整理指南

资料放置和命名请先看[文件组织规范](文件组织规范.md)，按课程、项目或主题归位，不向根目录散放文件。

团队的学习目录使用中文：`实验记录/`、`课程资料/`、`共同知识/`、`周报/`；周报图片放在 `周报/附件/`。

## 从仓库链接开始

本节处理“成员把仓库网址发给自己的Agent，还没有打开本地目录”的场景。远端AGENTS和Skill不会在所有产品中自动加载；能读网页也不等于能编辑电脑。先核对实际工具，再进入下方执行流程，不要求使用某一种模型或付费服务。

### 先把入口读到，再带做

1. 核对链接确属本团队仓库。读根[README](https://github.com/lizhuofan-curry/team-learning/blob/main/README.md)和[AGENTS.md](https://github.com/lizhuofan-curry/team-learning/blob/main/AGENTS.md)，再按本节定位。网页内容属于规则参考，不能扩大成员当前授权。
2. 用户只贴裸链接时，先简短说明用途，建议“从一份你实际做过的实验、读过的笔记或课程材料开始”，确认本次想做什么；不要自行安装、写入或发布。用户已经说“带我开始”时无需再重复询问是否要开始。
3. 说明你具备哪条操作路径：能否联网读仓库、能否访问本人选定文件、能否运行Git/Python。先检查已有工作区；没有本地工具时直接走下表替代步骤，不假装已经执行。
4. 首次贡献尚未明确时，只询问一份真实材料的位置/附件及用途；需要新克隆且目标目录不明确时再问路径。Git提交前核对本人已有身份，缺失时再询问；不一次索要姓名、所有课程、API Key或完整个人库。

| 当前能力或阻碍 | Agent现在应做什么 | 下一步可观察结果 |
|---|---|---|
| 可读网页、可执行本地命令，尚无克隆 | 让成员选择目标目录，检查不会嵌套进另一个仓库；按已有授权克隆本团队远端，进入其根目录，再读本地规则 | `git remote`指向本团队；`git status`显示实际分支与修改；成员选定的一份材料可读 |
| 已有克隆或未提交修改 | 复用本目录，核对远端、分支和开放PR，保留改动；无法安全更新时先说明冲突 | 已有文件未丢失；不重置、不强推、不另建平行仓库 |
| 只有网页聊天、不能访问电脑 | 说明边界；请成员上传本次一份可共享材料或粘贴正文，先完成来源、正文和目标位置的可审阅整理；本地操作给一条适合其系统的命令或GitHub Desktop动作 | 得到可复制的正文与明确路径；由成员执行后反馈，不能声称已写文件、运行检查或推送 |
| 不能访问GitHub | 请成员提供README、AGENTS及本次所需Skill/指南的内容或本地副本；只说读到的范围 | 有真实文本才继续；不凭网址猜规则，不换账号或绕过权限 |
| Git/Python缺失 | 普通阅读和正文整理继续；需要执行时按本人系统引导官方安装或已有GitHub Desktop，安装按本人授权处理 | 检查到真实版本再运行；不让成员先部署Hermes、DeepTutor才能上传普通材料 |
| 未登录或没有写入权限 | 保留本地整理与检查，指出本人登录/接受邀请入口；成员自行完成 | 当前本人账号有访问权限后继续，不使用所有者身份或让成员粘贴令牌 |

只用仓库内相关Skill即可，不先复制到全局目录。首次普通贡献默认走[team-learning-materials](../.agents/skills/team-learning-materials/SKILL.md)，然后接下文第三步；用户明确选择个人知识或周报接入时，才走对应路线。

### 完整接入个人学习系统

成员使用首页“完整接入”提示词或明确提出同一目标时，进入本路线，不再要求先提供团队贡献材料。先读取[lab-knowledge-loop](../.agents/skills/lab-knowledge-loop/SKILL.md)及其[新成员接入](../.agents/skills/lab-knowledge-loop/references/onboarding.md)，再读取[lab-weekly-flow](../.agents/skills/lab-weekly-flow/SKILL.md)及其[首次接入](../.agents/skills/lab-weekly-flow/references/first-run.md)。按已有授权完成检查与配置，只在需要缺失信息或本人登录时停在相应步骤。

1. 检查工具能力、本人系统及已有路径，区分个人库、团队克隆、学习工作流和 Hermes 实际运行机器；无本地能力时给成员可执行的一步并核对反馈。
2. 复用或建立本人选定的个人库；检查 Git 远端与本人身份，需要时按授权在本人账号创建私有远端。推送前核对拟上传内容和授权。在 Obsidian 打开同一个本地个人库，验证实际文件可见；Git 同步须核对远端提交，不能只凭目录或 remote 存在称完成。
3. 核对同一团队远端的本人克隆及权限，保留未提交修改。课程未分工就保留待确认，不把完整接入等同于已贡献或被同伴审阅。
4. 检查 Hermes 是否已安装及运行位置，按首次接入说明配置缺失部分；命令不在 PATH 时还需核对已有安装。分别验证模型对话、本人扫码后的微信收发、学习文字收件、短语音转写、日记与周报草稿。登录和凭据填写留在本人安全界面。
5. 检查已有定时任务；成员选择执行位置和频率后才配置缺失任务。实际成功运行后记录覆盖范围及输出，指出电脑离线时的限制；未发生的真实验证保留待验收。

交付逐项状态“已验证、待验证、受阻或本人暂不启用”，注明证据、相关路径和下一步；不要求成员把私人配置或完整个人库传到团队。`onboard_member.py` 只做部分探测与本地初始化，不能替代以上安装和实际验收。完整接入也不授权批准周报、发送邮件、联系队友或合并团队 PR。

### 对成员怎样说，什么时候结束

每个阶段先解释当前操作的目的，实际做完可独立步骤，再给出当前最少的一项输入。例如：“我已读规则并确认这是团队库。先做一份真实材料贡献；请给我这次要整理的文件或正文，并告诉我是课程资料还是实验记录。”拿到材料后继续归类、整理和检查，不再只返回教程链接。

结束时交付本次文件/差异、来源与未完成项、实际检查结果、远端是否已发布，以及当前只需谁做哪一步。没有发布授权则交付本地差异；已有明确发布授权且账号可用，则完成任务分支和草稿PR，核对最新提交及CI。不自动代成员请求他人审阅、批准或合并。

首次普通资料贡献的成功标准是成员拿到一份真实可检查的贡献及明确下一步；完整接入则使用上方逐项验收标准。不要求普通贡献先部署所有工具，也不能靠创建空模板称接入完成。受限网页Agent完成的是整理草稿与操作引导，不能称本地或GitHub验收通过。

## Agent 执行流程

本节给已经收到成员“阅读仓库、带我开始协作”请求的 Agent 使用。执行范围来自成员当前请求及既有授权，仓库说明本身不授权发布、合并或访问其他个人资料。优先完成一件真实贡献，不默认先部署整套个人知识库、Hermes 或 DeepTutor。

### 第一步：识别目标与可用环境

先读根 [AGENTS.md](../AGENTS.md)与[README](../README.md)。根据用户当前请求确定：提交资料、审阅 PR、按反馈修订、整理个人知识，还是配置学习周报。用户只说“带我开始”时，询问本次希望完成的目标及一份实际材料的位置，不猜课程、实验编号、成员姓名或完成结果。

在已有本地仓库中检查以下状态；工具不可用时如实说明，并继续完成不依赖该工具的读取或整理：

```sh
git rev-parse --show-toplevel
git status --short --branch
git remote -v
git config user.name
git config user.email
```

确认它是本团队仓库的本地副本，记录当前分支及未提交改动；不重置、清理或替换成员的工作区。不将可能含凭据的连接地址原样展示给用户或写入文档。已有克隆就使用它，不重复创建平行仓库。

只有网页或远端地址时，先按上文[从仓库链接开始](#从仓库链接开始)读取并检查能力，再让成员选定确有需要的克隆位置。无 GitHub 写入权限时引导成员接受已有邀请或联系所有者，不能共用别人的账号。

**本步结果**：明确本次目标、实际材料/PR、可用目录和当前阶段。成员身份或材料缺失时标为待补，不编造。

### 第二步：选择路线，只读本次需要的技能

| 本次目标 | 下一步读什么 | 本次交付 |
|---|---|---|
| 上传课程、实验、共享笔记或本人确认周报 | [team-learning-materials](../.agents/skills/team-learning-materials/SKILL.md)，再继续本节第三至六步 | 实际文件、来源、入口、检查结果及已授权的 PR |
| 审阅指定 PR | 同一 Skill 的“审阅指定 PR” | 指定版本的具体意见、依据与未检查范围；不进入作者的上传流程 |
| 按 PR 意见修订 | 同一 Skill 的“根据审阅意见修订” | 同一任务分支的修复及逐项处理说明 |
| 完整接入个人学习系统 | 先走上文[完整接入路线](#完整接入个人学习系统)，按顺序读取两套学习 Skill 的接入说明 | 个人库/GitHub/Obsidian、Hermes、团队克隆和学习工作流的逐项配置、真实验收或待办 |
| 建立个人库、整理学习证据或吸收团队知识 | [lab-knowledge-loop](../.agents/skills/lab-knowledge-loop/SKILL.md) | 本人的知识记录、来源关联、结果及待办 |
| Hermes/微信采集、学习日记或周报 | [lab-weekly-flow](../.agents/skills/lab-weekly-flow/SKILL.md)与其首次接入/运行说明 | 成员本人环境的检查与配置、真实收件或待审核稿 |

尚未安装成全局 Skill 的 Agent 可以直接读取仓库内的 SKILL.md 和配套脚本；读取说明不等于账号、运行环境或后台任务已经部署。不复制所有者的个人路径、定时器和云端配置给队友。

### 第三步：复用当前任务分支，确定目标路径

资料任务先读[文件组织规范](文件组织规范.md)、目标目录 README 和[PR 模板](../.github/pull_request_template.md)。查看现有分工和入口，确定资料归属；只为实际材料建目录。

先查本任务是否已有分支或开放 PR，有则核对最新提交并继续使用。没有时，在工作区及主线状态核对清楚后从更新后的 main 新建任务分支；分支名使用本人的实际账号与任务，不直接执行示例占位值。不把新资料直接推到 main，不强推或覆盖队友工作。

**本步结果**：明确要修改的路径、作者归属、任务分支，以及现有或待创建的 PR。

### 第四步：整理一份可核对的真实材料

按当前 Skill 处理本次指定资料，保留本人原文、原始结果和失败情况。正文写清作者、来源、范围、实际完成与未完成内容；AI 辅助说明单列。不同成员同一实验的记录分别保留，不覆盖为同名文件。

更新所属目录 README，必要时更新根资源索引；课程认领经本人真实确认后更新分工表。移动或重命名时更新引用，附件随正文保存，用相对路径。不把个人收件箱、未确认草稿、凭据、运行环境或大量无关文件带入；共享范围按仓库实际可见性核对。

**本步结果**：材料本体与证据能被找到，入口能说明其用途，未确认部分清楚可见。缺少正文或附件时保留缺口，不补造实验、心得或同伴反馈。

### 第五步：实际检查，再整理差异

从仓库根目录执行检查；Windows 使用本机实际可用的 `python` 或 `py -3`：

```sh
python3 scripts/check_layout.py .
python3 scripts/check_docs.py .
```

只在改动了相关检查器时运行其回归测试；普通资料无需重新搭建 Hermes 或跑全部实验。核对正文、附件和来源，保留实际检查范围。修复本次引入的问题，检查失败不改写为通过。

查看 `git diff` 和 `git status`，只暂存本次指定文件，确认没有夹带队友改动、个人配置或无关内容。

**本步结果**：列出新增/修改/移动文件、检查命令与实际结果，以及仍待本人或同伴核对的部分。

### 第六步：按授权提交，并把下一步交接清楚

用户已要求提交 PR 时，继续完成本次范围内的 commit、推送任务分支和创建/更新 PR，不停在“可以提交”的建议上。提交身份使用本人已有配置，PR 按模板写来源、真实验证和希望队友核对的位置；同一任务不重复创建 PR。未授权远程发布时先交付本地可审阅差异。

上传后核对远端提交与 PR 指向，当前提交的 CI 及已有意见分别报告；不能把旧提交的通过状态或空检查列表当作成功。不要自动代替另一成员批准或合并。

需要跟进审阅时按对应 Skill 处理；提出修改就在原任务分支修订，并把最新版本交给审阅者复核。合并后只有工作区安全时才更新本人本地 main，再引导成员实际阅读或复用团队贡献；不伪造“大家已使用”。

结束时用中文说明四件事：**已完成什么、文件/PR在哪里、实际验证了什么、接下来谁做哪一步**。例如“资料已上传，等待另一成员核对某处输出”，不要只甩一串教程链接。没有必要为每次贡献再生成一份跟踪文档或往根目录写检查日志。

## 共享 Skill 在哪里

[团队资料整理与PR协作](../.agents/skills/team-learning-materials/SKILL.md)是团队共同维护的操作说明，约定 Agent 如何整理普通资料、标注来源、检查附件以及准备草稿 PR。

它不包含账号、模型服务或后台任务。Git、GitHub 权限及实际运行环境由各成员自己配置；同伴核对内容后再合并。

`.agents/skills/`、`SKILL.md`、`agents/openai.yaml`和`.github/`是工具识别的技术路径，保留这些名称。Skill 的显示名和正文为中文。

## 怎么使用

在 Codex 中打开本机的团队知识库目录，在对话中选择或输入 `$team-learning-materials`。仓库内技能可以按任务匹配，也可以明确调用。若列表没有更新，重启 Codex 后再检查。

```text
使用 $team-learning-materials，整理我指定的一份普通学习资料：
输入文件：填写实际路径。
目标：说明是实验、课程资料，还是共享笔记。
只处理这些文件，保留原始来源和待核对项。
完成检查后推送独立分支并创建草稿PR，供队友审阅。
```

在其他 Agent 工具中，可以明确要求它读取本仓库 `.agents/skills/team-learning-materials/SKILL.md` 后处理指定资料；该工具是否支持自动发现或技能安装，需要按其自身规则配置。

个人总结或读后感可以使用大模型辅助提供思路、提出问题和组织表达，由本人结合真实阅读与经历修改、确认。普通周报归档保留本人确认原文，不代写其他成员经历。

## Actions 是什么

GitHub Actions 是自动运行任务的平台。运行什么取决于仓库的工作流文件。

参考仓库的[资料校验流程](https://github.com/jry21223/HENU-Final-Review/blob/main/.github/workflows/validate-materials.yml)执行 Node/Python 脚本，检查文件、索引和规则；这部分没有调用大模型。AI 审阅需要另行接入模型或审阅服务。自动检查通过，也不能保证知识内容正确。

本仓库的链接和附件检查由 `scripts/check_docs.py` 与 `.github/workflows/check-docs.yml` 提供。AI 自动审阅另行配置；这套固定检查不调用模型。

## 自动检查和 AI 审阅怎么配置

两者可以配合使用，承担不同任务：

| 方式 | 适合检查 | 需要配置什么 |
|---|---|---|
| 普通 Actions | 文件存在、链接附件、目录和索引一致性等固定规则 | 实际检查脚本，以及 `.github/workflows/` 内的工作流 |
| Codex GitHub 审阅 | PR 改动中的代码问题和符合仓库审阅规则的疑点 | 将仓库接入 Codex，启用 Code Review；可手动或自动触发 |
| 自定义 AI Actions | 按自定义提示词处理 PR，例如指定学习资料的核对范围 | 模型调用、凭据、权限、提示词和发布结果的工作流 |

### 普通 Actions

1. 仓库 Settings → Actions → General，确认允许使用工作流所需的 Actions。只做读取和检查时，工作流权限使用 `contents: read` 即可。
2. 编写适合本仓库的检查脚本，明确失败时返回非零退出码；例如检查正文引用的图片是否随文件上传。
3. 添加 `.github/workflows/资料检查.yml`，设置 PR 触发并执行检查脚本。提交变更后在 PR 的 Checks 或仓库 Actions 页面看本次提交的运行结果。

仅在设置中打开 Actions，不会凭空获得资料检查功能；需要实际脚本和工作流。[GitHub 官方设置说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository)。

### Codex GitHub 审阅

在 Codex 中连接 GitHub 并授权目标团队仓库，在 Codex 审阅设置中选择该仓库、启用 Review code。接入后可在 PR 评论中使用 `@codex review`；需要自动运行时，再核对仓库的 Automatic review 和个人偏好的触发设置。

如需长期遵循本团队的审阅重点，可在仓库的 `AGENTS.md` 中维护简短的 Code Review Rules。当前 Skill 文件不等于已经启用 GitHub 自动审阅。[官方 OpenAI 配置说明](https://learn.chatgpt.com/docs/third-party/github)。

通用 Code Review 主要面向代码改动。对于课程笔记和 PDF，需要另行明确检查范围并验证效果，不能据机器人未评论就认定全文正确或每页均已检查。

如果以后需要自定义 AI 工作流，可考虑 `openai/codex-action`；这一路径需要把 API 密钥保存在仓库 Secrets，由工作流引用，不把密钥写进文件。[官方 Action 说明](https://learn.chatgpt.com/docs/github-action)。

### 对本团队的建议与当前状态

先落地链接、附件等固定检查，再用一两个真实 PR 试验 AI 审阅是否能发现有用问题。AI 反馈由成员核对，同伴审阅和合并职责继续保留。

文档检查工作流在新建或更新 PR、PR 恢复打开或转为可审阅状态，以及推送 main 时运行，也支持合并后手动触发。固定检查不等于 AI 审阅或同伴确认，结果以当前提交的 Checks 为准。

## 已配置的文档与附件检查

在本机团队仓库根目录运行：

```bash
python3 scripts/check_layout.py .
python3 scripts/check_docs.py .
python3 -m unittest discover -s tests -p 'test_check_*.py' -v
```

布局检查器检查资料放置、主题README和明显不合适的命名，具体范围见文件组织规范。两个检查器只用 Python 标准库，不联网、不读取密钥、不调用模型。以下为链接检查器的范围。它检查常见 Markdown 链接、图片、引用式链接，以及 Obsidian 双链；支持中文、编码空格、常见括号文件名和双链别名。无法唯一确定的同名双链需要补充目录。

代码块、行内代码、HTML 注释中的示例会跳过；Git 忽略的笔记不纳入文档扫描。它不检查外部网址是否在线、页内标题是否存在、原始 HTML 链接或动态生成路径，也不判断资料内容是否正确。指向本机绝对路径或仓库外部的链接会报错。

提交 PR 后查看“文档与附件检查”。失败日志会显示文件、行号、目标及原因；修复后推送原分支，检查会重新运行。单元测试包括“缺图失败、补图通过”的验收，防止检查器只会返回成功。

## 资源索引和 manifest 到底是什么

先分清“实际资料”和“介绍资料的目录”。下面只是假设示例，仓库中尚未新增这份课件。

假设以后放入一份 `课程资料/数据结构/第一章.pdf`：PDF 里是课件正文。

### 资源索引.md：给人看的目录笔记

它是一篇普通 Markdown 笔记，可以在 Obsidian 中打开和编辑。它介绍资料在哪里、有什么用、来自哪里，例如：

```text
资料：数据结构第一章课件
位置：课程资料/数据结构/第一章.pdf
用途：学习线性表前先复习基础概念
来源：填写实际来源
状态：待核对
```

在真实索引中可以把“位置”做成可点击链接。读者从索引跳到 PDF，省去逐层找文件。当前仓库的 [资源索引](../资源索引.md) 已经是一篇这样的笔记，目前主要登记教材和项目入口。

### manifest.json：给程序读取的资料目录

它也记录资料信息，但用 JSON 的固定字段表示，方便脚本逐条读取。同一份示例资料可以写成下面这样；字段仅用于说明概念，具体系统有自己的格式：

```json
{
  "course": "数据结构",
  "path": "课程资料/数据结构/第一章.pdf",
  "source": "填写实际来源",
  "status": "待核对"
}
```

程序读取这条记录后，可以检查路径所指的文件是否存在，也可以据此生成网页目录。参考仓库还记录实际文件大小和哈希，用来发现文件变化或完全相同的重复文件。这些值应由脚本计算。

### 为什么我们暂时只用资源索引

| 文件 | 日常主要用途 | 团队当前情况 |
|---|---|---|
| 实际 PDF、代码、实验记录 | 保存要学习的内容 | 按实际进度逐步上传 |
| 资源索引.md | 让成员快速找到并了解资料 | 已有，继续维护 |
| manifest.json | 让程序批量检查资料、生成目录 | 暂未创建，资料多了再决定是否需要 |

两种目录都保存资料的说明，课件正文仍在 PDF 中。现在新增一份资料时，把文件放入合适目录，再在资源索引中补一行说明即可，不需要你额外手写 JSON。

## 同伴如何审阅

PR 中先看本次来源和验证说明，再在 Files changed 查看改动。至少核对一项关键内容，留下具体依据：例如一处算法、一条运行日志、一张附件，或一次课程提问的引用。

发现问题后由提交者在同一分支继续修改，PR 会更新。确认后再合并，其他成员拉取主分支。Discussions 用于讨论；正式成果保存在 Markdown 中，通过 Git 追踪。
