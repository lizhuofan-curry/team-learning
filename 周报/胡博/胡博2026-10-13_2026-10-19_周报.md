## 一、本周思考

### 1.个人Wiki搭建，RAG检索对wiki和个人学习的作用

通过本次搭建，我认识到 RAG 检索是知识库从“存储资料”转变为“辅助使用”的关键。普通知识库只能保存文档，RAG 能根据问题检索相关内容，再交给模型组织答案，并保留来源依据，从而减少无关回答和事实错误，提高知识复用效率。

对个人学习而言，RAG 可以把论文、代码、实验日志和笔记连接起来，支持跨文档提问、快速回顾和知识关联，减少重复查找资料的时间。同时，检索结果也能暴露知识缺口，帮助形成“阅读—记录—检索—验证”的学习闭环。它不能代替深入阅读，但能把分散的学习材料变成持续可查询、可追溯的个人知识助手。

### 2.agent记忆和知识库

**记忆不等于保存全部信息**：Agent 需要从对话中筛选、抽象和结构化有长期价值的内容，同时处理隐私、成本和信息过期问题。

**记忆能力应分层评估**：从基础回忆、多会话检索到主动服务，能力逐级增强；真正困难的是发现不同时间、不同会话之间的隐藏关联。

**存储格式需要权衡**：Simple Notes 成本低但缺乏关联，Advanced JSON Cards 表达力强但维护成本高，可执行状态则能支持规则检查和自动提醒。

**RAG 的关键不只是向量检索**：分块质量、稀疏与稠密检索融合、重排序以及上下文感知检索，都会直接影响最终效果。

### （四）Agentic RAG 与 Non-Agentic RAG 对比实验`[[agentic_ragmd]]`

在相同法律语料、问题集、回答模型和评审模型下，实验比较了单次检索的 Non-Agentic RAG 与基于 ReAct 的 Agentic RAG。7 个问题均完成，实验流程通过验收。结果表明，Agentic RAG 的优势主要体现在复杂问题，而不是所有问题上。

对于简单问题，两种方法的证据召回率均为 100%，平均检索次数均为 1 次，说明单次检索已经能够直接定位所需法条，继续进行推理和检索并不会带来明显收益。对于复杂问题，单次检索的平均证据召回率仅为 8.3%，而 Agentic RAG 提升至 91.7%；其中三个复杂问题由 0% 提升至 100%，最复杂的复合问题由 33.3% 提升至 66.7%。这说明问题分解、查询改写和基于证据缺口的补充检索，能够有效减少跨法条、多要素问题中的漏检。

这种覆盖率提升伴随着明显的资源代价。复杂问题的平均检索次数由 1 次增加到 3.5 次，平均延迟由 8.1 秒增加到 65.7 秒；全部问题的平均延迟也由 13.8 秒增加到 47.0 秒。因此，本实验支持的是一个有条件的结论：简单、单跳问题适合采用低开销的单次检索；复杂、含歧义或需要组合多条证据的问题更适合使用 Agentic RAG，但需要接受更高的时延和调用成本。

### （五）稠密向量检索实验：Annoy 与 HNSW 对比`[[dense-embedding]]`

本实验比较了两类主流 ANN 算法：基于随机投影树的 Annoy 和基于可导航小世界图的 HNSW。两种算法在最终实验中都达到 Recall@10 = 1.0，说明在当前 300 条文档的数据规模下，二者的检索准确率没有明显差异，主要区别体现在构建、查询和增量更新成本上。

| 指标        | Annoy（树结构） | HNSW（图结构） |
| --------- | ---------- | --------- |
| Recall@10 | 1.00       | 1.00      |
| 索引构建时间    | 13.20 ms   | 77.68 ms  |
| 平均查询延迟    | 0.234 ms   | 0.257 ms  |
| P50 查询延迟  | 0.226 ms   | 0.260 ms  |
| P95 查询延迟  | 0.263 ms   | 0.280 ms  |
| 索引文件大小    | 1.40 MB    | 1.02 MB   |
| 增量更新耗时    | 8.27 ms    | 33.83 ms  |
| 是否需要完整重建  | 是          | 否         |

Annoy 的特点是构建速度快、查询延迟略低，适合数据相对稳定、以批量构建和只读检索为主的场景。但它的索引更新需要完整重建，因此数据频繁变化时会带来维护成本，而且本次验证中还出现过特定运行环境下的 Annoy 扩展兼容性问题，最终通过 Docker 运行才完成稳定验证。

HNSW 的索引构建和增量插入更慢，但支持真正的在线更新，不需要完整重建；同时索引文件比 Annoy 小约 27%。因此，HNSW 更适合持续写入、实时更新和长期运行的向量数据库场景。它牺牲了一部分构建和更新速度，换取了更好的动态维护能力。

### （六）稀疏检索与 BM25 实验`[[sparse-embedding]]`

本实验采用从零实现的倒排索引与 Robertson/Sparck Jones BM25 算法，在 10 篇英文文档上进行验证，参数为 `k1=1.5`、`b=0.75`，返回前 5 条结果。

#### 实验结果

| 指标                        | 结果 |
| --------------------------- | ---: |
| BM25 手工计算与引擎结果误差 |    0 |
| 精确关键词 Recall@5         | 1.00 |
| 精确关键词 MRR              | 1.00 |
| 同义词查询 Recall@5         | 0.00 |
| 同义词查询 MRR              | 0.00 |
| 宏平均 Recall@5             | 0.80 |
| 宏平均 Precision@5          | 0.70 |
| 宏平均 MRR                  | 0.80 |

#### 稀疏检索的优点

1. **精确关键词匹配能力强**

   对错误码、产品型号、API 名称、技术术语和专有名词等查询具有较好的检索效果。实验中的 `XK9-2B4-7Q1` 等编码均能被准确定位。

2. **检索效率高**

   倒排索引只访问包含查询词的候选文档，避免了对整个文档集合进行逐一比较。本实验中索引构建耗时约为 `1.668 ms`，单次查询耗时约为 `0.095–0.276 ms`。

3. **结果可解释**

   BM25 的得分由词频、逆文档频率和文档长度共同决定。系统可以展示命中的词、词频、IDF 和各项得分，便于调试、分析和审计。

#### 稀疏检索的缺点

1. **语义理解能力有限**

   系统无法自动识别 `cat`、`kitten` 和 `feline` 之间的语义关系。查询词与文档词面不一致时，可能完全无法召回相关内容。

2. **对分词和词形变化敏感**

   拼写差异、缩写、词形变化和不同表达方式都可能导致匹配失败。当前实现没有词形还原、同义词扩展和语义改写能力。

3. **容易受到通用词影响**

   如果多个文档包含相同的普通词，系统可能返回只部分匹配的文档。例如 `HTTP 404 error` 召回了只包含 `error` 的文档，导致 Precision@5 降低。

#### 总结

本实验表明，传统稀疏检索具有**精确、快速、可解释和易部署**的特点，尤其适合错误码、产品型号、技术术语等词面明确的检索任务。但它的主要局限是**缺乏语义理解能力**，面对同义词、改写表达和隐含语义时容易漏召回。因此，稀疏检索适合承担精确匹配和关键词召回任务；对于需要理解语义的场景，可以将其与稠密检索结合，构建混合检索系统，从而同时获得词面匹配的准确性和语义检索的泛化能力。

### （七）用户记忆策略对比实验`[[user_memory]]`

用户记忆实验完成了 60 个测试用例、3 个任务层级和 4 种记忆策略的对比实验，共完成 240 次评估，最终运行的 1042 次 API 调用全部成功。

| 记忆策略              | 通过率 | 平均奖励 | 幻觉率 | 总 token  | 平均单次延迟 |
| --------------------- | ------ | -------- | ------ | --------- | ------------ |
| `enhanced_notes`      | 86.7%  | 0.8573   | 3.3%   | 987,468   | 32.17 秒     |
| `json_cards`          | 85.0%  | 0.8292   | 6.7%   | 1,126,107 | 40.55 秒     |
| `advanced_json_cards` | 81.7%  | 0.8156   | 3.3%   | 1,550,690 | 64.92 秒     |
| `notes`               | 80.0%  | 0.8031   | 3.3%   | 1,101,271 | 38.16 秒     |

因此，本实验的主要结论是：增加结构复杂度并不会自动带来更好的记忆效果。`enhanced_notes` 在综合准确性、跨轮上下文保持、幻觉控制、token 消耗和响应速度之间取得了最好的平衡；`json_cards` 更适合精确的单轮事实检索；`advanced_json_cards` 在复杂综合任务中具有潜力，但当前实现成本最高，且在多实体歧义任务中表现较弱。`notes` 可以作为轻量基线，但在复杂记忆场景下能力有限。
