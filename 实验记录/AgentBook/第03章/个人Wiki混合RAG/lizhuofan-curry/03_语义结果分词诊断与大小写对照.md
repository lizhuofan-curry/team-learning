# 语义检索偏题后的分词诊断

2026-11-01，本人完成wiki_dense_20261101_170733_090831，实际10批CPU嵌入、0次回答生成或网络请求。原来的6项技术检查通过，但Q1/Q2首位都是BCICIV2a数据集，明显不能支持对应定义；Q3首条EEGNet仍只是应用实例。保留这些结果，不记录成语义检索已经优于BM25。

## 已核对什么

Codex检查保存的65×512文档向量、3×512查询向量，形状、float32、有限值、L2范数及文件哈希一致。根据保存向量重新做点积及排序，与实际分数、Top-5一致。原始输入哈希、10批完成状态和冻结语料也一致，原record、向量和corpus均不修改；旁证另存原本地批次的核对记录。

这说明数值计算和落盘一致，仍不能证明输入保留了问题含义。原入口漏检了主查询词被编码成未知词元的情况。

## 发现的输入缺陷

当前固定BGE分词器配置do_lower_case=false，实际检查：

| 文字 | 特殊标记之间的实际词元 |
| --- | --- |
| Agent | [UNK] |
| agent | agent |
| Transformer | [UNK] |
| transformer | t、##ran、##s、##form、##er |

UNK表示分词器没有识别该段文字。Q1的核心Agent变成一个未知词元，许多语料中的大写英文术语也丢失信息；Q2查询本身虽是小写，但相关页面使用大写Transformer。代码原先只检查输出向量、跨度和截断，未发现这一缺陷。

另做3批合成诊断，权重加载无缺失或多余键；一个合成查询单独与批量编码完全一致，eager与默认SDPA在该小样本的最大绝对差约1.94e-7。该有限诊断未发现批处理或注意力实现异常，不等于证明所有后端都无问题，也不是新的正式检索排名。

## 下一步只改输入大小写

运行明确的独立对照：

```bash
<本人项目目录>/.venv/bin/python '<本人项目目录>/第三章/个人Wiki混合RAG/我的代码/03_同一快照的中文语义检索.py' --casefold
```

此选项在送入嵌入模型前，对文档片段及带指令的查询统一casefold，英文转小写；中文问题内容保持原义。BM25本来就在切词时做casefold。原Wiki、冻结文本、片段ID/跨度、三题原句、模型版本、CLS池化、查询指令、seed、batch和Top-5均不变。

新结果存到wiki_dense_casefold新批次，记录输入规范化类型、实际模型输入哈希及查询UNK数量，保留未规范化批次与脚本快照。65块加3查询仍最多10批本地嵌入，0次回答生成和网络请求；不重新下载模型或读取实时Wiki。

只读分词检查显示，三个查询的UNK数量由1/0/0变成0/0/0；全部片段中的UNK总数由596降为125，剩余未知词元可能来自公式、符号等，不能说全部文本已被完美编码。该检查没有执行新的嵌入前向，也没有改变排名。

casefold能解决已确认的大小写信息丢失，是否改善实际排名仍待本人运行验证。尤其脑机接口题可能缺少一般定义资料，分词修正不能凭空补入知识。此时先做这一有明确原因的输入对照，不调模型、权重或语料来追逐更好结果；相关性金标、RRF融合与回答生成仍未完成。
